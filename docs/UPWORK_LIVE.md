# A4: Live Upwork connection

The implementation uses the official `https://mcp.upwork.com/mcp` endpoint through `MultiServerMCPClient` and Streamable HTTP. No Upwork page is scraped or browser-automated. The user completes authorization in their own browser.

Implemented:

- Settings → Connect Upwork initiates the MCP SDK OAuth flow, dynamic client registration and PKCE S256. OAuth state is validated and consumed once. An interrupted authorization must be restarted; pending PKCE state is intentionally memory-only.
- Access/refresh tokens and dynamic registration credentials are encrypted with Fernet in a per-user SQLite vault. Token expiry and OAuth metadata persist so a fresh client can refresh tokens. The key comes from `OAUTH_ENCRYPTION_KEY` or a separate local key file with restricted permissions. Keep the original key backed up separately from the database. Tokens never go to localStorage or API responses.
- The common marketplace port chooses the provider per authenticated application user, including background graph tasks and workers. A pending graph is bound to its original connection; switching providers cannot retarget an already reviewed proposal.
- Authenticated MCP discovery saves the real account's tool schemas. Operation mappings are validated against that catalog; no fixture tool name is assumed to exist on Upwork. A changed catalog invalidates mappings. A unique freelancer account is selected automatically; ambiguous account selection fails closed. Settings supports full live mode or a read-only mode that refuses writes.
- Pre-approval previews are local and side-effect-free. After GigBid approval, the official proposal `create` action prepares a provider preview; mandatory invitation/proposal checks run first and incomplete pages stop preparation. The provider's proposal tool is annotated destructive because it groups several actions; only its documented preview-producing `create` branch is allowed at this stage. The official message tool sends directly, so message text is staged locally instead. Both return `awaiting_platform_confirmation` and zero Connects spent by GigBid so far.
- A separate **Confirm on Upwork** panel shows the complete preview/action, requires a fresh confirmation checkbox, and asks about proposal attachments/highlights. The authenticated, run-owner-scoped confirmation endpoint binds approval to the preview digest and original account connection. Only this second action calls official `confirm_preview` or `send_message`. No write is executed as a connection test. A successful provider response is stored as `platform_confirmation_recorded`, not fabricated as a verified submission/hiring outcome. Inspect the account for the actual outcome. File upload/highlight selection is not implemented here; choosing attachments blocks final confirmation until that workflow is completed.
- Live writes require explicit graph approval, get a durable intent before network I/O and are never automatically retried. A timeout/crash leaves an uncertain record requiring account inspection; it cannot silently duplicate a write. Read retries are bounded and identical reads are cached for 60 seconds. Scheduled live scouting is disabled by default; enabling it requires explicit opt-in and an interval of at least 15 minutes.

## Connect locally

Run `python -m scripts.run_gigsim --with-api` and `python -m scripts.run_frontend`. Open Settings, sign in, then choose Connect Upwork. The default callback is `http://127.0.0.1:8000/connections/upwork/callback`. It must match the URI registered in the OAuth flow. A hosted deployment needs its own HTTPS callback in `UPWORK_CALLBACK_URL`, a persistent `OAUTH_DB` and a persistent encryption key shared by API/worker. The local auto-generated key is not committed. `Disconnect Upwork` deletes local credentials; revoke GigBid in Upwork's account settings to revoke provider access too.

This app currently uses synthetic personas/portfolios for its assignment demonstrations. Connecting an account does not make those claims real. The approval gate blocks live proposals from a profile explicitly marked synthetic. Real proposal drafting requires the user's actual verified portfolio/profile; no live proposal or message is used as an automatic connection test.

## Tool contract verification after consent

`GET /connections/upwork/catalog` returns the authenticated user's discovered schemas and digest. Known official mappings are configured automatically for a unique freelancer account. Advanced mappings can be reviewed through authenticated `PUT /connections/upwork/mapping` with `catalog_sha256` and `operations`. Six read operations map job, client, balance and conversation reads. Generic provider drafts require non-destructive annotations and a confirmation link; official Upwork instead uses its documented proposal-preview action and locally staged messages, followed by the separate platform-confirmation gate. Settings activates full live mode or read-only mode. Connecting alone leaves simulator mode selected. Mapping endpoints are a developer interface, not an LLM tool.

Actual names, arguments and output shapes come from authenticated discovery and read-only `get_tool_help`. The current adapter maps `find_jobs`, `get_profile`, `get_messages`, client history returned by full job details, the documented proposal-preview action and locally staged messages. Unknown application cost in a search result stays null until job details provide it. Client work history is a provider sample, not a fabricated complete history. Unknown message sender-side/response structures fail closed. `tests/fixtures/upwork_oauth_app.py` is explicitly a local fixture, not an official schema.

## Evidence and current limits

The official public server successfully initiated OAuth and returned an Upwork authorization URL using PKCE S256; this was verified without signing in or making account writes. Sanitized evidence: `evals/results/upwork_public_discovery.json`.

Local integration tests use the actual SDK against a protected HTTP MCP fixture and cover PKCE, state mismatch/replay rejection, encrypted token persistence, refresh, all port methods, API callback flow, user isolation, provider switching, official action-specific proposal preparation and both human gates. They assert that the first approval creates a preview but executes nothing, and that a separate owner-approved confirmation executes exactly once. Message staging also executes nothing until a separate confirmation. Unit tests cover unsafe mappings, connection binding, real read-response normalization and uncertain-write replay prevention. Python results are recorded in `evals/results/upwork_adapter_tests.json`; browser results are in `upwork_playwright.json`. The typed API client regenerated and the frontend production build passed.

On 14 November 2026 the user completed real Upwork authorization. The account exposed 33 tools. Live read-only checks passed for account selection, search, one full job, its client record, Connects balance and room listing through the common port; writes were locally refused during the smoke test. Sanitized evidence is in `evals/results/upwork_live_verification.json`. No proposal, message or final confirmation was sent, and no Connects were spent. This account has no existing rooms, so live message-history normalization remains unverified. Proposal-preview and final-execution contracts are tested locally against provider-shaped fixtures, not by sending a real application. Synthetic demonstration profiles remain blocked from live proposals. These limits are not claims of live write success.

The SDK expiry/metadata hydration shim is tested with MCP 1.30.0 and langchain-mcp-adapters 0.3.2; revalidate it when upgrading. OAuth connection tasks currently live in one API process; reconnect after a restart or use sticky routing for authorization callbacks in a multi-process deployment. The per-user write-intent ledger is durable across processes, while read caches are per process. Keep live account mode changes explicit in Settings; authorization alone does not switch the inbox to live Upwork.
